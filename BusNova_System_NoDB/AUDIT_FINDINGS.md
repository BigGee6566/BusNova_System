> **Methodology note, 2026-09-23 (FIX-017):** no finding, but it cost a day and it will cost the next reader a day too if it is not written down. **PowerShell's `Invoke-WebRequest` disposes the response stream on a 4xx/5xx before the body can be read**, so *every* error page in this application reads back as an empty body. Measure error responses with a raw `[System.Net.HttpWebRequest]`, catching `WebException` and reading `$_.Exception.Response`, and the pages render exactly as they should. The cost of not knowing this: on the false reading an `<httpErrors existingResponse="Replace">` block was added to `Web.config`, which overrides `Response.TrySkipIisCustomErrors` and broke every error page in the application — a real defect introduced to fix one that did not exist. Both changes were reverted. The general lesson is the one AUD-054 taught in a different key: **an instrument that cannot see a thing is not evidence that the thing is absent.** Several rounds in this engagement were spent on measurement artefacts — `border-collapse`, a stale ViewState captured before an app recycle, this disposed stream — and telling those apart from product defects is a skill this document should record, not just the defects themselves.

> **Methodology note, 2026-09-23 (WP-12):** a second instrument problem, of the same family as the `Invoke-WebRequest` one above, and it nearly produced a false bug report. **An HTTP client that sends no `User-Agent` header gets a materially different page from ASP.NET.** Browser-capability detection decides `SupportsJavaScript`, and with no agent string the framework omits `WebResource.axd`, the `__doPostBack` definition and the whole client validation script — while still rendering `href="javascript:__doPostBack(...)"` on every LinkButton. Measured that way, `ManageUsers.aspx` appeared to have 11 calls to a function that was never defined, which reads exactly like "every LinkButton in the application is dead". It is not: the same request with a Chrome `User-Agent` defines `__doPostBack` and registers all seven payment validators, and the page grows from 14,015 to 21,363 bytes. **Always set a `User-Agent` when measuring a Web Forms page.** The rule this keeps proving: an instrument that cannot see a thing is not evidence that the thing is absent — and here the instrument did not merely fail to see, it changed what the server produced.

> **Withdrawn prediction, 2026-09-24 (WP-13):** recorded because a wrong hypothesis that was checked is worth as much as a right one. Alongside AUD-063 I predicted a matching defect: `.form-control` and `.form-select` are defined in `Styles/style.css`, which is also page-level, and five pages use those classes without linking it — so their inputs should have had no padding, no border radius and **no focus ring**, which would have been a WCAG 2.4.7 failure as well as a cosmetic one. It was going to be AUD-064. Measured first, as the plan required: `ValidateTicket`, `Manifest` and `ReportTicketSales` all report `border-radius: 6px`, `padding: 12px`, `border: 0.8px` — identical to pages that do link `style.css`. **Bootstrap is loaded globally by `Site.Master` and already styles those classes.** The prediction was plausible, symmetrical with a defect that is real, and wrong. Had it been written up from reading alone it would have entered this document as a High-severity accessibility finding that did not exist.

> **Withdrawn finding, 2026-09-24 (WP-14):** the sidebar appeared to stop about 1,000px down a 1,730px page, leaving a dead white column beside the content for the rest of its length — visible in a full-page screenshot of `ManageUsers.aspx`, and exactly the kind of thing the brief meant by "no dead space". Measured before writing it up: the sidebar is `position: fixed` with `height` equal to the viewport, which is correct — a fixed sidebar stays in view as the page scrolls rather than stretching to the document. **`Page.captureScreenshot` with `captureBeyondViewport: true` renders the full document height while a fixed element paints only its own box**, so the empty column is an artefact of how the picture was taken and does not exist in a browser. A viewport-only screenshot taken after scrolling to y=1200 shows the sidebar fully painted. Same family as the 28 false overflow failures in WP-13 and the missing `User-Agent` above: the instrument, not the product. The cost of checking was one screenshot; the cost of not checking would have been a fix to a layout that is already right.

The build is clean, the test suite is green, the CSRF and page-guard coverage is genuinely complete, the password hashing is exactly what the documentation claims, and every SQL statement in the codebase is parameterised. Those are real strengths and the audit confirmed each one by evidence rather than by reading the comments.

The problems are concentrated in four places:

1. **No reporting exists at all.** Not one of the four reports the Project 6 brief requires is implemented, and neither is any report named in the Sprint system matrices. This is the single largest gap against the brief.
2. **The passenger booking path has never successfully completed.** The live database holds zero `Booking` rows, zero `BookingCreated` audit entries, and every `Ticket` row has a `NULL BookingID`. Two confirmed defects in that path explain why it would fail under tampering, and it is unexercised even under normal use.
3. **The deployed database does not match its own creation script.** The seat-uniqueness index is unfiltered in the live database, which permanently blocks resale of any cancelled seat, and no migration script exists that would ever fix it.
4. **Passenger-facing ticket numbers are derived from `MAX(TicketID)+1`, not from the identity value.** The live data proves the two have already diverged.

**Checked:** token issuance and validation coverage handler by handler, cookie flags, headers, hashing, SQL construction.

**Passed.** The CSRF token is rendered once into a hidden field on the single shared `<form runat="server">` in `Site.Master:22`, refreshed per request at `Site.master.cs:44`, and **every state-changing postback handler in the application validates it.** Verified individually: `AssignRoute:74`, `BookTrip:144`, `CreateRoute:27`, `IssueTicket:175` and `:258`, `LogFuel:129`, `Login:52`, `MaintenanceWork:51` and `:103`, `ManageUsers:43`, `:99`, `:132`, `MyTickets:40`, `PaymentSimulation:115`, `Register:32`, `RegisterBus:28`, `ReportIssue:49`, `RequestPasswordLink:26`, `SetPassword:54`, `TicketConfirmation:75`, `ViewAssignedRoutes:42` and `:95`. ### Verification results

- **Build and markup:** `Verify.ps1 -SkipTests` was clean (MSBuild and `aspnet_compiler`) after every change.
- **Unit and markup-guard tests:** **258 of 258 pass**, including the seven `MarkupGuardTests`: one version per asset, one `h1` per shell page, and every grid wired for responsive labels. They were run from a local copy because of UI-018. From the OneDrive working copy no test can execute on this machine, and the script now says so.
- **Measurement sweep after the fixes:** every Manager page at 1280, 1024, 768 and 375px, and every Driver, Maintenance and Passenger page at 1280, 768 and 375px. It found zero overflow, zero tables scrolling in their wrapper, zero contrast failures, zero small targets on shell pages and zero heading skips.
- **Functional paths exercised after the changes:** sign-in and sign-out for all four roles, the Live Map tile success and refusal paths, passenger search through to the seat map, and My Tickets with both viewable and non-cancellable tickets. No functional regression was found. One SQL Express connection timeout during sign-in, logged in `App_Data/Logs`, succeeded on retry and is unrelated to these changes.
- **Console and network:** a fresh Home page load makes zero failed requests.

### Remaining issues

- **UI-019:** `launch.json` should point at whichever copy is actually run.
- **Test data in the development database** shows through the UI as junk, for example the bus registration `4FOTFYU7YUI;` and maintenance entries such as `tkdfhiug...`. That is data rather than presentation, and it was not edited.
- **`IssueTicket`'s "Validate a ticket" panel** overlaps the Validate Ticket page, since both look up a ticket by number. Merging them is a workflow decision, so it was left.
- **The tile provider.** `tile.openstreetmap.org` remains a volunteer service unsuitable for production volume, as `live-map.js` already states. UI-008 makes a refusal visible and recoverable, but it cannot guarantee tiles.
